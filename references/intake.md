# 接收要求：把用户的话变成可核对的清单

先确认用户的要求、来源和允许修改的范围，用可以复查的方式记录会影响成稿的事项。

## 一、要求的四种来源

| 来源 | 怎么读 | 注意 |
|---|---|---|
| 对话文字 | 逐句拆成条目 | "好看一点"这类模糊词要追问或给出可执行解释 |
| 图片（截图、手写、照片） | 用 **adaptive-vision-skill**，native 模式优先 | 读出的字号、字体、版式必须转成文字条目，不能凭印象 |
| 附件（docx / pdf / tex / 模板） | 用 docx、pdf 对应 skill 读 | 附件只读；要改先复制到 `PROJECT_ROOT` |
| 样例（"照这篇的样子"） | 提取格式特征，不照抄内容 | 区分"必须一致"和"仅供参考" |

## 二、确认改动范围和验收依据

- 新写先确定目标载体、结构、篇幅、摘要、引文、公式、图表和交付格式。提取与当前任务有关的要求。
- 局部修改先定允许修改的位置，注明必须保留的正文、素材、样式、分页和编号。只追加时优先把新内容放在末尾；原页需一致时，用同一工具渲染前后文件并比对该页。涉及编号、目录、链接等联动项时核对其实际影响。
- 纯排版保留原文、段落、链接、引文、图表、公式和字段。对照文本及结构，核对要求保护的页或对象。合并或拆分段落、修改文字、统一术语属于另外的改动，须在授权范围内。
- 给定模板时记录它约束的是版式、结构还是两者。老师后续补充和新版文件用于替换冲突的旧要求，记录适用版本。
- 标出交付类型、文件名、是否需要可编辑源稿，以及需要用户填报、确认或披露的事项。只有用户确实要求的材料才纳入交付。

## 三、留存适量记录

沿用项目记录，或用一份工作记录保存「要求/来源 → 取值或范围 → 验收证据/待确认项」。对正文或数据有硬性数量要求时，写清字数、页数或统计口径。简单修改可在交付说明简述。结构化状态使用「已落实、待确认、不适用、未达到」，按实际结果填写。

## 四、优先级裁决

| 冲突情形 | 裁决 |
|---|---|
| 用户 vs 官方模板 | 用户明确要求优先于一般建议。若与指定载体的硬性条件不能同时满足，指出具体冲突并请用户裁决 |
| 用户 vs 领域优秀论文惯例 | 按用户 |
| 用户 vs 本 skill 默认值 | 按用户 |
| 用户要求之间自相矛盾 | 问一次，给两个选项和推荐 |
| 用户未规定 | 官方规则 → 领域惯例 → 默认值 |

## 五、模糊要求的处理

- "专业一点""好看一点""像正式论文"：不要自己猜完就算。给出一组具体取值（字号、行距、配色）作为默认，并在清单里注明"按默认执行，可改"。
- 用户说"你看着办"：视为授权使用默认值，但仍要在清单里写明用了什么。
- 用户前后说法不一致：以后一次为准，并在清单里标注前一条作废。

## 六、进入执行

按已知范围执行；遇到会改变任务结果、且无法从材料确定的冲突再问。新稿按 [格式调研](format-research.md) 补齐缺项；已有稿件按更改范围沿用当前规格，只查受影响的项目。
